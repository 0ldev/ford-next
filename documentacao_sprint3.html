Organização e separação clara de responsabilidades

Clean Architecture nas duas pontas, mesma separação de camadas — cada uma só conhece a de baixo:

CamadaBackendFrontend
domainRegra pura, sem I/O: hash de senha e JWT (security.py), escopo por perfil (authorization.py), score de risco, ação recomendadaTipos/contratos que espelham o schema da API

Pipeline (ETL/treino do modelo) roda offline, por fora da API — o servidor web nunca processa o dataset bruto dentro de uma requisição HTTP.

Fluxo de comunicação e autenticação da solução

  1. Login — POST /api/auth/login com {usuario, senha} (único endpoint de dado público, além de /health)
  2. Validação da senha — o servidor confere o hash (PBKDF2-HMAC-SHA256 + salt); nunca compara texto puro
  3. Emissão do token — 200 com {token, perfil, dealerCode, expiraEm}; o front salva a sessão em localStorage
  4. Requisições seguintes — todo apiGet/apiPost do front anexa automaticamente Authorization: Bearer <token>
  5. Validação do token — dependencies.py::obter_usuario_atual decodifica e verifica assinatura/expiração a cada requisição
  6. Autorização por perfil — domain/authorization.py resolve o escopo: gestor passa livre; concessionaria só acessa o próprio dealerCode, senão 403

Implementação de autenticação e controle de acesso

Autenticação via usuário/senha → JWT (ver seção 3). Controle de acesso via 2 perfis, aplicado como dependência do FastAPI (Depends(obter_usuario_atual)) em todo endpoint de dado:

3. JWT 15%

Geração e validação de JWT

Biblioteca PyJWT, algoritmo HS256. Geração e validação isoladas em domain/security.py:

criar_token(usuario, perfil, dealer_code) -> (token, expira_em)
decodificar_token(token) -> TokenPayload  # levanta TokenInvalidoError se inválido

Claims: sub (usuário), perfil, dealerCode (null para gestor), iat/exp.

Proteção dos recursos utilizando token

HTTPBearer como security scheme do FastAPI + Depends(obter_usuario_atual) em todo endpoint de dado — token ausente, malformado ou com assinatura inválida vira 401 antes de qualquer lógica de negócio rodar. Isso também registra o esquema no OpenAPI, habilitando o botão "Authorize" no Swagger (ver seção 6).

Expiração e uso adequado das informações do token

  • Expira em 60 minutos (JWT_EXPIRA_MINUTOS) — token expirado é rejeitado com 401, testado com token gerado com expiração negativa.
  • Segredo de assinatura via variável de ambiente JWT_SECRET (fallback de desenvolvimento, documentado como inseguro para produção).
  • Senha nunca em texto puro: PBKDF2-HMAC-SHA256 (600.000 iterações) + salt aleatório por usuário, comparação com secrets.compare_digest (evita timing attack).
  • dealerCode vem do claim assinado, não de nada que o cliente envie — impossível de forjar sem quebrar a assinatura HMAC.

4. Maturidade REST — Nível 2 20%

APIs orientadas a recursos

URLs são substantivos (recursos), não verbos: /leads, /leads/{vin}/acao, /leads/{vin}/contatos, /vin-share, /trend/concessionarias, /anomalies, /catalogo, /resumo-executivo, /auth/login. O recurso /leads/{vin}/contatos foi adicionado nesta sprint especificamente para demonstrar um recurso com estado (registro persistido), não só leitura.

Uso adequado dos métodos HTTP

VerboUso
GETtoda leitura — nunca muda estado no servidor
POST/auth/login (gera uma sessão) e /leads/{vin}/contatos (cria um registro de contato, persistido em CSV)

Status codes coerentes com cada operação

200leitura ou login com sucesso

401sem token, token inválido/expirado, credenciais de login erradas

6. Documentação e Tratamento de Erros 10%

Documentação da API com OpenAPI/Swagger

Swagger UI nativo do FastAPI em /docs (spec crua em /openapi.json), com:

  • Metadata: título, versão (1.0.0) e descrição da API;
  • Tags por recurso (Autenticação, Leads, Tendência, Anomalias, Catálogo, Resumo executivo) — Swagger agrupado por área;
  • Botão "Authorize" funcional (esquema HTTPBearer registrado automaticamente) — cola o token e testa qualquer endpoint protegido direto pelo navegador.

Padronização das respostas de erro

Handler global (main.py) intercepta toda HTTPException e toda exceção não tratada, devolvendo sempre o mesmo formato — sem quebrar o contrato já existente (detail continua string):

{ "detail": "Usuário ou senha inválidos.", "codigo": "NAO_AUTENTICADO" }
{ "detail": "VIN 'x' não encontrado na lista de leads.", "codigo": "NAO_ENCONTRADO" }
{ "detail": "Erro interno no servidor.", "codigo": "ERRO_INTERNO" }

codigo é estável (NAO_AUTENTICADO, PROIBIDO, NAO_ENCONTRADO, DADOS_INVALIDOS, ERRO_INTERNO) — o front-end pode decidir comportamento (ex.: forçar novo login em NAO_AUTENTICADO) sem parsear a mensagem. Erros 500 nunca vazam stack trace ao cliente (só logados no servidor).
